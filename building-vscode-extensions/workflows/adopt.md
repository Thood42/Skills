# Adopt: bring an existing extension up to the standard

Use when the user wants an existing extension (not generated by this skill) made maintainable
to this standard. The principle is a **ratchet**: stop new violations immediately, then burn
down old ones in small behaviour-preserving slices. Big-bang rewrites of working extensions
fail; this does not.

```
Adopt progress:
- [ ] 1. Inventory
- [ ] 2. Adoption baseline report
- [ ] 3. Ratchet: vendor the checker, waive existing findings with expiry, wire CI
- [ ] 4. Migration plan through the feature gates
- [ ] 5. Execute slices (safety net first)
```

## 1. Inventory

Record in `docs/plans/adopt-baseline/inventory.md` (create the folder):

- Build: tsc-only / webpack / esbuild; where `main` points; is it bundled?
- Tests: framework, runner (`@vscode/test-electron` direct vs `@vscode/test-cli`), unit vs
  integration split, do they run in CI?
- CI/CD: provider, how the VSIX is produced and distributed today, who installs it how.
- Structure: where VS Code calls live vs logic; size of `extension.ts`; global state.
- Manifest: activation events, engines vs `@types/vscode`, capabilities, settings shape.
- Users: which VS Code versions are deployed (this sets the engines floor).

## 2. Adoption baseline report

```bash
node scripts/vsx-check.mjs <repo> --gate release
```

Use the release gate so majors show up too. Summarize the findings by category and record
them in `docs/reviews/<date>-adoption-baseline.md` (you may run `scripts/gate.mjs --gate
baseline` instead if the repo's scripts already work). Add the judgment rules that obviously
fail (for example ARC-J01 handlers without error boundaries, ARC-J02 disposables not owned).

## 3. Ratchet

Make new violations fail CI before fixing any old one:

1. Copy `scripts/vsx-check.mjs` to `tools/vsx-check.mjs`; add
   `"check:extension": "node tools/vsx-check.mjs"` to `package.json` scripts; add a CI step
   running `npm run check:extension -- --gate slice`.
2. For each existing finding, propose a waiver (rule + path + "pre-existing at adoption" +
   expiry by when the migration plan fixes it). The user approves the list — they are human
   decisions — and you write `docs/reviews/waivers.json`.
3. Add `AGENTS.md` (start from `assets/template/base/AGENTS.md.tmpl`, adapted to the repo's real
   layout and commands) and `docs/adr/0001-adopt-baseline.md` describing the target state.

From here, any new blocker fails CI while legacy ones are tracked with an expiry.

## 4. Migration plan

Run the migration as a software-factory feature named `adopt-baseline` (`workflows/feature.md`):

- Gate 1: no user-visible change; success metric = open blockers to zero by a date, and no
  behaviour regressions reported.
- Gate 2/3: target structure and the order of moves; which template files are copied
  (`assets/template/base/`), never overwriting existing files blindly.
- Gate 4 slice order (safety net first, then structure):
  1. **Test harness**: `@vscode/test-cli` + `.vscode-test.mjs` + the "every contributed command
     is registered" integration test. Nothing else moves until this runs in CI.
  2. **Bundling**: esbuild + allowlist `.vscodeignore`; compare `npx vsce ls` before and after.
  3. **Manifest hygiene**: activation events, engines/@types pin, capabilities, settings,
     categories.
  4. **Layering**: one feature per slice — extract pure logic into `src/core/` with unit
     tests, move VS Code calls into `src/features/<name>/`, route commands through
     `registerCommand()`.
  5. **Strictness**: TypeScript `strict` (per-folder if needed), lint rules, remove waivers.

Each slice ends with the slice gate and removes the waivers it resolves. Behaviour must not
change: the integration tests from slice 1 prove it.
